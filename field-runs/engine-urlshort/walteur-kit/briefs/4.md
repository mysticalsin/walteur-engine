## Design slice (design-of-record)
# Design Doc — Zero-Dependency Node URL Shortener (`engine-urlshort`)

## 1. Goal & Contract
A zero-dependency (runtime AND dev) Node.js HTTP JSON API for URL shortening:
- `POST /shorten` with JSON body `{ "url": "<http(s) url>" }` → `201 { code, shortUrl }`.
- `GET /:code` → `302` redirect with `Location: <original url>`, empty body.
- In-memory `Map<code,url>` store; resets on process restart (per requirement).
- Strict, typed-error input validation (reject non-http(s) schemes + malformed/missing/non-string input).
- Collision-safe short codes via bounded regenerate-on-collision.
- A `node:test` suite that drives the running server over REAL HTTP using only `node:http`.
- A README documenting endpoints, the typed-error table, run/test commands, and explicit non-goals.

**Stack (verified on Node v24.13.1, Active LTS):** `node:http` server, `node:crypto` for codes, `node:test` + `node:assert/strict` for the suite. Pure ESM (`"type":"module"`), explicit `.js` extensions on relative imports. `engines: {"node": ">=20"}` — floor at 20 (node:test stable since 20; we test on 24 LTS where subtest auto-await closed the silent-pass footgun). Cross-platform npm scripts only (Windows dev host — no bash-only invocations).

## Build standard
Stack: Node.js (built-in node:http server, node:crypto for code generation, node:test + node:assert for the test suite). Zero third-party dependencies. package.json with "type":"module" (ESM) and a "test" script. Node 18+ (for stable node:test).. Build to current best (2026-07-02): RUNTIME: Node.js 26 is Current (released 2026-05-05, latest patch v26.4.0), Node 24 is Active LTS (the safe production target), Node 22 is Maintenance LTS (EOL approaching — do not target as the floor for a new project). For a new zero-dependency microservice, set package.json "engines": {"node": ">=18"} only if you truly need 18.x compatibility for node:test stability; otherwise prefer ">=20" or ">=22" since node:test's subtest-completion semantics changed materially in Node 24 (subtests now auto-await/complete before the parent finishes — no more silent-pass bugs from forgetting `await t.test(...)`), so testing on Node 24 LTS is the safer baseline even if the engines floor stays at 18. NOTE: starting with Node 27 (Oct 2026) Node moves to ONE major release/year with all releases becoming LTS — irrelevant to this build but worth knowing the cadence is changing.

MODULE FORMAT: "type":"module" (pure ESM) remains the 2026 default recommendation for new Node projects — confirmed still current, not superseded. Use explicit .js extensions on all relative imports (ESM requires this; no change from prior guidance).

TEST RUNNER: node:test + node:assert/strict remains the correct built-in-only choice (no supertest/jest needed for zero-dep constraint). Use `node --test` (stable since Node 20, refined in 24) with node:assert/strict for clearer diffs. Code coverage via `--experimental-test-coverage` is CONFIRMED STILL EXPERIMENTAL as of Node 26.4.0 — flag it as experimental in the README/tests rather than presenting it as stable; it cannot currently be combined cleanly with certain reporter flags (long-standing nodejs/node#47669, still relevant). Prefer `node --test` with the default spec reporter for the HTTP integration suite; add coverage only as an optional/documented extra, not a hard requirement. Use t.before/t.after/beforeEach/afterEach hooks to spin up/tear down the node:http server once per suite (listen on port 0, read the OS-assigned ephemeral port, close in `after`).

CRYPTO FOR CODE GENERATION: Use node:crypto's randomBytes(n).toString('base64url') (or randomUUID() where a full UUID is acceptable) for short-code generation — base64url is the current idiomatic encoding for URL-safe tokens/short codes (no manual base64 replace() hacks needed, base64url has been a native encoding option for years and remains best practice). If any comparison of secrets/codes happens server-side (e.g., API-key checks), use crypto.timingSafeEqual() to avoid timing attacks — call this out explicitly if the service has any authenticated/admin endpoints.

HTTP/SECURITY: node:http.createServer is NOT deprecated and remains fully supported in Node 26 — safe to build directly on it per the stack requirement; only the internal node:_http_* submodules are deprecated (irrelevant here since only the public node:http API should be used). 2026 JSON API security baseline to bake in: always set Content-Type: application/json on responses (and reject/ignore mismatched request Content-Types) to avoid MIME-sniffing XSS; validate AND sanitize all input server-side (structure + content, not just structure); apply per-IP/per-key rate limiting on any mutating or lookup-heavy endpoints (hand-rolled token-bucket/sliding-window is fine and idiomatic for a zero-dep service); never leak stack traces or internal errors to clients — return a consistent {error:{code,message}} envelope and log full detail server-side only; if the service ever handles auth, treat JWTs as stateless-but-short-lived (access token ~15 min) — likely out of scope for a plain URL-shortener-style API but worth flagging if auth gets added later.
