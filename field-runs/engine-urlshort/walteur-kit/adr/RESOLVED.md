# ADR 0001 — How are short codes generated — random opaque codes (collision-safe by retry) or a sequential/counter-based scheme?
Status: ACCEPTED
## Decision
Option A — Random opaque codes: crypto.randomBytes(6) -> base64url (8 chars), inserted via a bounded has()-guarded regenerate-on-collision loop in store.save(), throwing typed CODE_GEN_EXHAUSTED (500) on cap-out.
## Why
Lowest-risk for THIS build because random is already the ratified, spike-verified contract and every other deliverable is built to it — reversing it is the larger, riskier change. Concretely: (1) The typed-error taxonomy already lists 500 CODE_GEN_EXHAUSTED (PLAN.md §5 table, line 57) and §6 names 'request hang on code exhaustion' as an owned failure mode with its own test (line 69); sequential deletes a spec-listed error code and a named failure mode. (2) PLAN.md §2 line 21-22 marks 'crypto.randomBytes(6).toString(base64url)' and 'collision-safe = BOUNDED retry' as empirically re-verified decisions flagged do-NOT-re-litigate, and AGENTS.md §5 plus .claude/rules restate bounded-retry-only as mandatory — so random is the option the contract, three rule files, and the README error table (which must match src/errors.js byte-for-byte) already encode. (3) Advocate B's strongest attack — that the collision/exhaustion branch is dead code untestable without mocking the RNG — is already defeated by the build's own architecture: PLAN.md §3 line 31 makes store.save injectable ('inject a stub generator / pre-seed the map') and §7 line 77 + testing.md make a forced-collision-to-CODE_GEN_EXHAUSTED test a REQUIRED deliverable, so the branch is honestly reachable over the store seam, not vacuous green. (4) Advocate A's own concessions hold: it is a zero-dep core one-liner adding ~3 lines and one typed error that matches the spec's pervasive typed-error idiom, and at 48 bits over an in-memory Map the retry loop effectively never spins. Security (non-enumerability, no volume leak) is a genuine secondary win for a public GET /:code redirector, but the decisive factor here is contract/test/README alignment, not the threat model.
## Rejected
Random codes: crypto.randomBytes -> base64url (~8 chars), inserted with a bounded regenerate-on-collision loop against the Map, throwing a typed CODE_GEN_EXHAUSTED on cap-out. Unpredictable and non-enumerable, at the cost of a retry path and an exhaustion error branch. — trade-off: Sequential base62 counter's real advantage is a strictly simpler, failure-free write path — collision-free by construction, so no retry loop, no CODE_GEN_EXHAUSTED branch, no cap constant to get wrong, and shorter codes across the realistic range (=<6 chars to ~56B URLs vs. a fixed 8). Rejecting it means we keep a near-never-taken loop and one extra typed-error branch. The cost of that trade is accepted deliberately: the loop is exercised only via an injected stub in the required collision test (not real traffic), and choosing sequential would force rewriting PLAN.md §2/§4/§5/§6/§7, the error registry, the byte-for-byte README table, and the collision test — a far larger blast radius against an otherwise fully-specified build — while also making public codes enumerable (GET /1,/2,/3 walks the whole store) and leaking total URL volume off any single code. Advocate B's proposed strictly-dominating fix (keyed Feistel permutation over the counter: non-enumerable AND collision-free AND no exhaustion branch) is genuinely elegant but is neither of the two options on this fork and imports scope/complexity the zero-dep, do-not-re-litigate build did not fund — a strong choice for a different build, not a lower-risk move for this one.
