## Blockers / open (also in ISSUES.md — ordered worst-blast-radius first)
- [audit/major/security-exposure] Host-header reflection into shortUrl is undocumented. Live-verified: POST /shorten with `Host: evil.example.com` + `X-Forwarded-Proto: https` (and BASE_URL unset, which is bin/server.js's default) returns shortUrl 'https://evil.example.com/<code>'. The stored/redirected href is safe (canonicalized, unaffected), so this is not an open redirect, but a consumer that renders/emails/treats the returned shortUrl as canonical can be pointed at an attacker-chosen origin. blind-review.json already flagged this 'important'. The README's non-goals list (SSRF, persistence, auth, rate-limit, dedup, vanity, TLS/CORS) does NOT mention this header-trust boundary, so 'validated' is silently conflated with 'trusted origin' for shortUrl. -> fix: Add one non-goal bullet to README.md §4 stating shortUrl is derived from client-controlled Host/X-Forwarded-Proto when BASE_URL is unset and must not be trusted as canonical without a fronting BASE_URL or Host allowlist. Optionally validate Host against an allowlist (or require BASE_URL) in src/server.js buildShortUrl when no override is set.
- [audit/minor/degraded-ux] Broken shortUrl on a genuinely-absent Host header. Live-verified via a raw HTTP/1.0 request with no Host header: buildShortUrl (src/server.js:120-128) does `${proto}://${req.headers.host}/${code}` with req.headers.host === undefined, producing shortUrl 'http://undefined/<code>' — a non-navigable, malformed URL returned as a 201 success. bin/server.js never sets BASE_URL, so the fallback branch is always the one that runs. HTTP/1.1 mandates Host so most clients are unaffected, but this is an unhandled edge at a trust boundary that ships a broken artifact instead of a typed error or sane fallback. -> fix: In src/server.js buildShortUrl, guard for a missing/empty Host: fall back to the server's bound address (e.g. via req.socket.localAddress/localPort) or a configured default, or reject with a typed error, rather than interpolating undefined.
- [audit/minor/degraded-ux] HEAD /:code returns 405 METHOD_NOT_ALLOWED (Allow: GET) instead of being handled like GET. RFC 9110 §9.3.2 expects a resource that supports GET to also support HEAD (headers only, no body). Live-verified: HEAD on a valid code -> 405. Low impact for this API's use case but a spec deviation. -> fix: Treat HEAD like GET in the /:code route (respond 302 + Location with no body), or document HEAD as unsupported. Optional given scope.
- [audit/minor/degraded-ux] Stale build documentation. AGENTS.md §2 still reads 'No package.json exists yet (pre-build)' and '# TODO: fill in — package.json not yet created', but package.json now exists with the exact npm test/npm start scripts. A maintainer reading AGENTS.md §2 is told the project is unbuilt and the commands are a TODO. (The README has the correct, current commands.) -> fix: Update AGENTS.md §2 to reflect the shipped package.json scripts (test -> node --test, start -> node bin/server.js) and remove the pre-build TODO block.
- [audit/minor/cosmetic] blind-review.json nit still open: readBody() JSDoc (src/server.js:58-60) and the 'error' handler comment (lines ~100-103) say it rejects 'after destroying the socket'/'the destroy() above', but the over-cap path actually calls req.pause() (destroy would kill the still-owed 413). Runtime is correct (413 with Connection: close verified) but the comments describe an earlier design and could lead a maintainer to reintroduce destroy() and break 413 delivery. -> fix: Correct the readBody JSDoc and inline comments to describe the pause+resume+Connection:close flow that is actually implemented.
