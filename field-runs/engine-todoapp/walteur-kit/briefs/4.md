## Design slice (design-of-record)
# Design Doc — Accessible Zero-Dependency Todo SPA

## 1. Problem & success

A keyboard-and-screen-reader user manages a personal task list in a single browser tab. Success is precise and testable: **every** action (add / toggle / edit / delete / filter all|active|done) is operable by keyboard alone with correct **announced** ARIA state; tasks survive reload via `localStorage`; and a `node:test` suite over the **pure** state logic passes green **with zero third-party dependencies** (runtime AND dev). The app runs by opening `index.html` — no install, no build.

Non-negotiable constraints that shape every decision below:
- **Zero deps, runtime and dev.** `node:test`/`node:assert/strict` are Node built-ins → the dependency tree stays empty. No jsdom, no framework, no bundler, no transpiler, no third-party test mock.
- **Pure logic must be DOM-free.** The state module imports under `node:test` with no shim. This forces a ports-and-adapters split.
- **Runs from `file://`.** ES modules + `localStorage` only; no build artifact.

### Architecture decisions in force
- ADR 1: When the persisted localStorage payload parses as JSON but contains some malformed todo items (e.g. one item missing `id` or with a non-boolean `done` inside an otherwise valid array), what should the loader do — the plan itself leaves this open as 'item dropped OR whole load rejected'? → CHOSE Option B — All-or-nothing: if ANY item fails the SHAPE_GUARD, reject the entire payload and resolve to []. deserialize stays a total function whose corrupt-path contract is: not-JSON | not-array | version>current | ANY item mistyped -> []. On rejection the loader does NOT removeItem the raw blob (leaves it forensically recoverable) and the app surfaces a one-line non-blocking status so the failure is LOUD, not silent. (rejected Partial recovery: keep every well-formed item and silently drop only the invalid ones, so a single corrupt record never costs the user their whole list.)
- ADR 2: How should the active filter's state be exposed to assistive tech — the DoD leaves it as 'aria-pressed (or aria-current)', which are semantically distinct? → CHOSE Model the three filters as a native <button> toggle group using aria-pressed="true|false" on every control (exactly one true). This is Advocate A's option. (rejected Model the three filters as a toggle-button group using aria-pressed=true/false on <button> controls (pressed/unpressed toggle semantics).)

## Build standard
Stack: Vanilla JavaScript (ES modules), semantic HTML5, CSS — zero runtime dependencies. Node.js built-in node:test + node:assert as the only test tooling (dev-only, no third-party packages). Browser Web Storage API (localStorage) for persistence. No package manager install required to run the app; package.json only declares the test script.. Build to current best (2026-07-02): RUNTIME/VERSIONS: Node.js 26 is the "Current" release (v26.4.0 as of this research); Node.js 24 is Active LTS (the version to target/document for a dev-only test tool); Node.js 22 is Maintenance LTS (EOL approaching, avoid as the stated minimum for new work). Node has ALSO just announced a release-model change taking effect Oct 2026 (one major/year in April, LTS promotion in October, every release becomes LTS eventually) — worth a one-line footnote in docs but not an implementation change today. Recommend package.json "engines" target >=22 (safe floor) with docs noting 24.x as the actively-tested LTS.

TEST TOOLING (node:test + node:assert, dev-only, zero third-party deps — exactly this project's constraint):
- node:test is stable and the correct choice (has been stable since Node 20; nothing supersedes it for a zero-dependency policy).
- Use `node --test` (glob-based auto-discovery of *.test.js / test/**) rather than hand-listing files.
- Prefer `node:assert/strict` (or `import assert from 'node:assert/strict'`) over legacy loose `node:assert` — strict mode is now the idiomatic default in current docs/examples.
- TestContext now exposes `t.assert.*` (e.g. `t.assert.deepStrictEqual`, `t.assert.snapshot`) as scoped assertion helpers bound to the running test — current idiomatic code increasingly calls `t.assert.X` inside a test body instead of importing `node:assert` separately, though both remain valid and node:assert/strict is still perfectly current for a minimal zero-dep layer.
- Snapshot testing (`t.assert.snapshot`, `--experimental-test-snapshots`, `--test-update-snapshots`) exists but is still experimental — do NOT treat it as required/stable; fine to skip for a "pure-logic unit test layer" that just needs deterministic assert-based checks.
- Code coverage via `--experimental-test-coverage` (with `--test-coverage-lines/branches/functions` thresholds) remains EXPERIMENTAL, not stable, even in Node 26 — flag this if any generated docs imply it's a stable/GA feature.
- Use subtests (`t.test()` inside a parent test) and `describe`/`it` BDD-style wrapper (also in node:test) as both are current stable idioms; plain `test()` + subtests remains the leaner, more idiomatic choice for a pure-logic layer with no BDD framework dependency.

JAVASCRIPT/ES MODULES: Import attributes (`import data from './x.json' with { type: 'json' }`) are STABLE (no longer experimental) as of Node 22+ and have solid cross-browser support (Chromium, Firefox; Safari trailing) — this is the current way to import JSON in ESM, superseding the old `assert { type: 'json' }` syntax (that older `assert` keyword syntax is now deprecated/removed in favor of `with`). Flag if any older material still shows `assert { type: 'json' }` — that's stale.

CSS: Native CSS nesting, `:has()`, and container queries are all now Baseline/production-ready across evergreen browsers (90%+ support each) — a "vanilla CSS, zero dependencies" app in 2026 should use native nesting and container queries directly rather than reaching for a preprocessor; Sass/PostCSS are no longer necessary for a project with this stack's "zero runtime dependencies" ethos. This is a genuine shift from a training-era default of "you still need a preprocessor for nesting."

ACCESSIBILITY: WCAG 2.2 (AA) remains the current, legally-referenced standard (ADA/Section 508/EAA). WCAG 3.0 is still only a W3C Working Draft — Candidate Recommendation not expected until ~Q4 2027, final recommendation no earlier than 2028. Continue building/testing against WCAG 2.2 AA and the W3C ARIA Authoring Practices Guide (APG) patterns; do NOT redesign around WCAG 3.0 draft criteria. Also note the current, more nuanced guidance on APG: treat APG patterns as a reference for how ARIA *should* work, not a blind "use ARIA roles everywhere" checklist — prefer native semantic HTML5 elements over ARIA-heavy widgets wherever native elements suffice (this refined "ARIA anti-patterns" framing is a recent-ish (2026) community correction worth noting).

STORAGE: For this domain's stated need (small preference/state persistence via Web Storage API), localStorage remains the correct, current choice — no supersession. Current 2026 guidance draws the line at ~5MB/sync-only limitations: reach for IndexedDB only when data exceeds simple key-value preference state, needs structured/binary data, or must not block the main thread. Given the stated stack explicitly scopes to localStorage for a small SPA, this is still best practice, not a stale pattern.

PACKAGE.JSON: No install-required app + test-only package.json remains valid/idiomatic for a zero-runtime-dependency project. Recommend `"type": "module"` for native ESM (no build step), a single `"test": "node --test"` script, and an `"engines": { "node": ">=22" }` floor reflecting current LTS reality..
