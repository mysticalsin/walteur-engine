# ADR 0001 — When the persisted localStorage payload parses as JSON but contains some malformed todo items (e.g. one item missing `id` or with a non-boolean `done` inside an otherwise valid array), what should the loader do — the plan itself leaves this open as 'item dropped OR whole load rejected'?
Status: ACCEPTED
## Decision
Option B — All-or-nothing: if ANY item fails the SHAPE_GUARD, reject the entire payload and resolve to []. deserialize stays a total function whose corrupt-path contract is: not-JSON | not-array | version>current | ANY item mistyped -> []. On rejection the loader does NOT removeItem the raw blob (leaves it forensically recoverable) and the app surfaces a one-line non-blocking status so the failure is LOUD, not silent.
## Why
Grounded in the actual PLAN.md at field-runs/engine-todoapp/PLAN.md (fork is line 67; SHAPE_GUARD/failure-modes in §3, contract in §4). Three build-specific arguments decide it, all from Advocate B: (1) The plan ALREADY commits to this contract — §3/§4 list `[{}]` (an array containing a malformed item) as a mandatory wrong-shape case that resolves to []. Partial recovery would directly contradict the case-3 contract the plan already wrote and closed; B preserves it, A re-opens it. (2) The non-boolean-`done` trap is unanswerable under A given §3's hard constraint 'done: strictly true/false (never truthy coercion)' — an item with valid id/text but non-boolean done forces A to either drop it (destroys a wanted todo over one field), coerce it (silent invention the plan EXPLICITLY forbids), or keep it (invariant lie that breaks toggle/filter and re-persists corruption). Every A branch violates a pinned constraint; B's reject-the-envelope has one coherent answer. (3) Testability is a Definition-of-Done constraint here, not a preference: .claude/rules/testing.md §3 mandates one test() block per shape-guard case and forbids catch-alls, and machine-readable proof reports must hold. All-or-nothing is a total function with ~2 equivalence classes (fully provable across the enumerated null/42/'str'/{}/[{}] -> [] cases); partial recovery explodes into a per-field drop/coerce/keep + survivor-order + duplicate-id matrix — exactly the untested-branch surface where silent data loss hides. Tie-break: A's costs are UN-mitigable within its own frame (cannot preserve the invariant, cannot answer non-boolean done without coercion, cannot bound the test surface), whereas A's one genuine benefit (don't annihilate bulk data) IS reproducible inside B by keeping the raw blob recoverable + a loud status line. Lower-risk = the option that keeps the boundary provably total and never lets a mistyped field leak past the trust boundary. That is B.
## Rejected
Partial recovery: keep every well-formed item and silently drop only the invalid ones, so a single corrupt record never costs the user their whole list. — trade-off: Rejecting Option A (partial recovery) has a real, honest cost, which is Advocate A's genuine strength: a personal todo list IS an independent-record collection with no cross-item invariant and a single JSON.stringify writer, so the realistic '199 good, 1 bad' corruption means all-or-nothing discards good user data to satisfy a strict-integrity symmetry the data does not inherently have. That loss lands hardest on exactly the keyboard/screen-reader user this app is built to serve, for whom re-entering a lost list is most expensive — 'never cost the user their whole list' is a real value B trades away. B accepts that trade only because it recovers most of A's benefit (raw blob preserved for recovery + loud status on reject) WITHOUT taking on A's structural liabilities — silent partial forgetting, the non-boolean-done coercion dilemma the plan forbids, and the combinatorial, partially-untested corrupt-path matrix that would ship the branches where data quietly disappears.

# ADR 0002 — How should the active filter's state be exposed to assistive tech — the DoD leaves it as 'aria-pressed (or aria-current)', which are semantically distinct?
Status: ACCEPTED
## Decision
Model the three filters as a native <button> toggle group using aria-pressed="true|false" on every control (exactly one true). This is Advocate A's option.
## Why
For THIS build (single-page, vanilla JS, no router, no history) nothing navigates, so aria-current's spec-blessed values (page/step/location) don't apply and you fall back to the generic aria-current="true" escape-hatch — a semantic hedge, not a fit. aria-pressed is valid on the native <button> the DoD already requires, needs zero role scaffolding, and keeps the keyboard model free/native (Tab + Enter/Space). Decisively for a build whose deliverables are a node:test suite plus a byte-matched a11y-contract.json: aria-pressed yields a TOTAL view function — every button's aria-pressed = String(btn.filter === state.filter), giving a clean, testable invariant (exactly one true, two false) that the proof report can byte-match. B's own strongest evidence (APG: mutually-exclusive toggles should behave like radio buttons) does NOT lead to aria-current — it leads to radiogroup/aria-checked or tablist/aria-selected, both of which require hand-rolling roving-tabindex + arrow-key navigation in vanilla JS, which is net-new error-prone code and higher proof-drift risk in a deliberately no-framework build. B advocates against aria-pressed persuasively but never makes a positive case for aria-current specifically, and concedes it's only the 'lightest-touch' fallback.
## Rejected
Model the three filters as a toggle-button group using aria-pressed=true/false on <button> controls (pressed/unpressed toggle semantics). — trade-off: The real cost of rejecting the current-item-in-a-set model: aria-pressed is a genuinely looser semantic match for a mutually-exclusive selection than a radio/tab set — the ARIA spec authored 'pressed' for self-contained on/off switches, and screen readers announce three independent 'pressed/not pressed' binaries rather than one positional 'current/selected', so the user must infer the mutual exclusivity rather than have it conveyed. If this filter ever becomes a real hash-route (#/active) or grows into a genuine view-switcher, aria-current="page"/aria-selected would become the literally-correct token and aria-pressed a category error requiring a rework of the markup and the a11y-contract.json. The README's Accessibility Notes must state plainly that filters are toggle buttons (WAI-ARIA button pattern) to preempt the reviewer question 'why not a radio/tab single-select?', since that is the honest weak seam of this choice.
